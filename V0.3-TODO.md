Based on a deep analysis of `ffi.rs` and `engine/engine.rs`, here are the features currently missing or "trapped" in the Rust layer (not yet exposed to C++), as well as architectural gaps in the core engine.

### 1. FFI Exposure Gaps (Rust has it, C++ doesn't)
While the Rust core is quite capable, the `ffi.rs` layer is missing several critical management functions:
*   **Serializable Transactions:** `engine.rs` defines `SerializableTransaction` (with version-checking and conflict detection), but `ffi.rs` provides no way to start one. Currently, C++ can only do "Atomic Batches" (blind writes), not true "Read-Modify-Write" transactions.
*   **Security Rule Configuration:** The `set_security_rules` function exists in Rust, but there is no `fl_engine_set_security_rules` in the C header. You cannot define access policies from C++.
*   **Composite Index Creation:** Rust has a `create_composite_index` method, but `ffi.rs` lacks an entry point for it. Users are stuck with collection scans unless indexes are hard-coded in Rust.
*   **Subcollection Helpers:** While the engine supports them via string pathing, there are no specific FFI helpers for them (e.g., `fl_engine_get_subdocument`). The user must manually format the `col:id/subcol` string.
*   **Audit History Access:** You can enable the audit log via config, but you cannot retrieve the `AuditEntry` list through the FFI.

### 2. Document Model Gaps
The `FireLiteDoc` in Rust supports `Value::Map`, but the builder API in `ffi.rs` is flat:
*   **No Nested Objects:** There is no `fl_doc_insert_doc(parent, key, child_doc)`. You cannot build a Firestore-like nested map structure from C++.
*   **No Array Support:** There is no `Value::Array` in the `value_to_json` conversion or an `fl_doc_insert_array` in the FFI.
*   **No Partial Updates (Merge/Patch):** To update one field, you must `Get` the whole doc, modify it, and `Put` it back. There is no `fl_engine_update` that modifies just one key without sending the whole document over the FFI boundary again.

### 3. Query Engine Limitations
The `Query` struct and its executor are missing several standard database features:
*   **No Logical `OR` or `IN`:** The query planner only handles a `Vec<Filter>`, which the executor treats as a series of `AND` operations. You cannot perform a query for `status == "active" OR status == "pending"`.
*   **No Offset support:** You have `Limit`, but no `Offset`. This makes implementing pagination in a UI very difficult.
*   **No Joins/Relations:** As a document store, this is expected, but there is no "Document Reference" type to automate fetching related items.
*   **Query Snapshot Isolation:** The query engine uses an `Arc<RwLock<StorageEngine>>`. While thread-safe, it doesn't appear to provide a "Point-in-Time" snapshot. If a large query is running and a batch commit happens, the query might return some "old" and some "new" data.

### 4. Administrative & Maintenance Gaps
*   **Explicit Compaction Control:** `engine.rs` has a `compact()` method, but it isn't exposed to `ffi.rs`. You have to rely on the background maintenance thread or closing the engine to trigger it.
*   **Storage Statistics:** There is no way to query the engine for its "Live" size vs. "Ghost" (deleted) size, or to see how many segments are currently active.
*   **Collection Deletion:** You can delete documents, but there is no `fl_engine_delete_collection` to drop an entire namespace and its indexes instantly.

### 5. Performance Opportunities (Missing Optimizations)
*   **No Query Caching:** Every call to `fl_query_execute` goes through the planner and executor from scratch. There is no prepared statement/query plan cache.
*   **FFI String Overhead:** As noted in your benchmarks, every string passes through `cstr_to_string` (UTF-8 validation + allocation). A "StringView" or "Blob" approach for keys could speed up the FFI significantly.
